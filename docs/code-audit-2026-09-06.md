# 교집합 코드 점검 — 2026-09-06

## 범위와 결과

현재 작업 폴더의 코드를 기준으로 앱·공통 코드 243개 TS/TSX 파일의 구성과 참조를 조사하고, 신청·티켓·멤버십·결제·피드백·인증·채팅 흐름을 중점적으로 읽었다. 운영 DB는 피드백 권한과 참가 상태 변경 함수의 정의만 읽어서 검증했다. 운영 데이터에 대한 변경이나 공격성 요청은 하지 않았다.

전체 코드의 모든 분기를 실행한 검증은 아니다. 브라우저 전 구간 E2E, 실결제, 부하 테스트, 프로덕션 빌드는 수행하지 않았다. 웹훅과 WaitlistAdminPanel 등에 이미 있던 미커밋 변경을 포함한 현재 작업 트리 기준이므로 배포된 코드와 동일하다고 단정하지 않는다.

- `npm run test`: 27개 파일, 133개 테스트 통과.
- `npm run typecheck`: 실패. 현재 폴더의 `analysis/` 내부 TS 파일에서 19개 오류가 보고됐다. 해당 디렉터리는 현재 Git 미추적 상태이므로 깨끗한 체크아웃의 CI도 실패한다고 단정할 수 없다.
- 추가 `noUnusedLocals` / `noUnusedParameters` 검사: 앱의 미사용 함수·컴포넌트·인자 확인.
- 코드 및 DB 수정 없음. 이 점검 문서만 추가. git push 없음.

## 먼저 해결할 오류 위험

### 1. P1 — 피드백 API의 검사를 DB 직접 쓰기로 우회할 수 있음

근거:
- `src/app/api/meetings/my-tickets/feedback/route.ts:300`: 티켓 소유·확정 상태 검사.
- 같은 파일 `:316` 이후: 제출 가능 시간 검사, `:400` 이후: 같은 행사 대상인지 검사.
- `supabase/migrations/20260817053456_harden_database_permissions_and_rls.sql:129`: 피드백 쓰기 정책은 `auth.uid() = user_id`만 검사.

운영 DB에서도 authenticated 역할의 INSERT/UPDATE 권한, 동일한 정책, 추가 사용자 트리거 없음이 확인됐다. 따라서 자기 user_id로 직접 저장하거나 수정하면 API에 있는 시간·참가 상태·대상 검사와 완료 처리 절차를 거치지 않는다. 정상 제출 후 관심 대상 변경이나 잘못된 행사 연결로 매칭 자료가 오염될 수 있는 구조다. 실제 악용 사례를 확인한 것은 아니다.

개선: 브라우저의 피드백 직접 쓰기 권한을 닫고 검증된 서버 경로만 허용하거나, 동일 검증을 DB 함수로 옮긴다. 피드백 저장과 참가 상태 변경은 한 트랜잭션으로 묶는다. 기존 클라이언트의 직접 쓰기 의존성을 먼저 검색한다.

### 2. P1 — 중복 신청이 기존 확정 티켓을 대기로 되돌릴 수 있음

근거: `src/app/api/meeting-date-applications/route.ts:565`, `:659`; `supabase/migrations/20260701100000_ticket_domain_restructure.sql:358`.

기존 신청을 protectedRows로 분류해서 신청 행 저장을 건너뛰어도, 멤버십 사용자와 선택 티켓이 있으면 참가 상태 변경 함수를 다시 `waitlisted`로 호출한다. DB 함수는 기존 상태를 그대로 덮어쓴다. 현재 운영 함수 정의도 동일하다. 마감 전 기존 approved 신청에 동일 티켓으로 다시 POST하면 신청 행은 approved인데 참가 티켓은 waitlisted가 될 수 있다. 새로 전달하는 간단한 ticket_snapshot으로 예약자명 등 기존 스냅샷도 대체될 수 있다.

개선: 기존 신청의 허용 상태를 먼저 검사해서 완료된 중복 요청에는 기존 결과를 반환한다. 신청 저장·참가 상태 변경·연결을 한 트랜잭션으로 묶고, approved → waitlisted 같은 전이는 명시적인 운영 명령에서만 허용한다. 같은 날짜의 다른 행사까지 연결하는 `user_id + meeting_date` 갱신도 신청 id 기준으로 좁힌다.

### 3. P1 — 처리 중 종료된 결제 알림이 영구 누락될 수 있음

근거: `src/app/api/webhooks/groble/route.ts:1413`, `:1438`; `supabase/migrations/20260720170000_groble_webhooks.sql:21`.

이벤트를 먼저 received로 저장한다. 이후 서버 종료나 강제 시간 초과로 catch가 실행되지 않으면 failed로 바뀌지 않는다. 동일 알림 재전송 시 failed가 아닌 모든 상태를 중복 성공으로 반환하므로 received 상태의 미처리 결제가 다시 처리되지 않을 수 있다. 이미 일부 반영된 경우에는 여러 테이블의 부분 반영 문제도 생긴다.

개선: received/processing/processed/failed를 구분하고 작업 점유 만료시간을 둔다. 오래된 received/processing은 재시도하고, 완료 여부 확인과 결제 반영은 원자적으로 처리한다. 단순히 received를 모두 재실행하면 동시 중복 처리 문제가 생기므로 잠금·멱등성까지 같이 설계해야 한다.

### 4. P1 — 멤버십 시작일과 누락된 종료일을 유효성 검사에서 놓침

근거: `src/features/membership/membershipTypes.ts:80`, `:92`; 호출부 `src/app/api/meeting-date-applications/route.ts:413`.

startDate를 인자로 받지만 실제 함수에서 사용하지 않는다. 종료일이 없으면 유효한 것으로 처리한다. 로컬에서 실제 함수를 실행해 다음 두 경우 모두 true임을 확인했다.

- active, 시작일 없음, 종료일 없음.
- active, 시작일 2099-01-01, 종료일 2099-12-31.

따라서 잘못 저장된 active 상태나 미래 시작 멤버십이 무료 참가 혜택으로 이어질 수 있다. 이전에 확인한 ‘날짜 없는 active’ 현상과 연결되는 경로지만, 누가 어떻게 그 상태를 만들었는지는 이 결과로 알 수 없다.

개선: `시작일 ≤ 오늘 ≤ 종료일`을 공통 기준으로 사용하고, 무기한·운영진 제공 혜택이 필요하면 별도 명시적 유형으로 표현한다. 기존 데이터 보정과 경계값 테스트를 함께 한다.

### 5. P2 — 분석 파일이 앱 타입 검사 범위에 섞임

근거: `tsconfig.json:26` 전후의 `**/*.ts`, `**/*.tsx` 포함 규칙; 위 실제 검사 실패.

서비스와 무관한 분석 스크립트가 동일한 타입 검사 대상이라 현재 로컬 검증을 막는다. 앱 타입 오류와 운영 분석 오류를 분리해서 볼 수 없다.

개선: 앱 tsconfig의 검사 루트를 명확하게 정하고 분석은 별도 tsconfig/실행 환경으로 분리한다. 타입 오류를 무시하는 빌드 옵션으로 우회하지 않는다.

## 구조·성능 개선

### 6. 상태와 장소 정보의 기준이 여러 곳에 존재

meeting_date_applications, ticket_participations, meeting_events/groups/stages, ticket_instances, ticket_snapshot을 함께 읽고 여러 경로에서 쓰고 있다. `my-tickets/route.ts`가 상당 부분을 병합·추론해서 표시하며 호환 fallback도 유지한다. 단순한 중복 필드가 아니라 데이터 간 일관성을 계속 맞춰야 하는 구조다.

권장 경계:
- 행사/그룹/단계: 일정·장소의 기준.
- 신청: 접수·결제 대기 및 승인 결정.
- 참가: 확정 멤버와 도착·참여·피드백 상태.
- 결제: 결제/취소 이력과 혜택의 근거.
- 스냅샷: 명시한 시점의 기록. 최신 운영 정보의 우선 소스로 섞어 쓰지 않기.

먼저 각 필드의 소유자를 정하고 공통 서비스/DB 명령으로 쓰기 경로를 모은다. 이후 기존 티켓 모델을 단계적으로 축소한다. legacy라는 이름만 보고 삭제하면 현재 기능이 깨질 수 있다.

### 7. P2 — 그룹 이름으로 피드백 범위를 추론함

근거: `src/app/api/meetings/my-tickets/route.ts:462`, `:512`; `src/app/api/meetings/my-tickets/feedback/route.ts:68`, `:369`.

그룹 번호 1~3 및 7은 123, 나머지는 456이라는 규칙이 박혀 있다. 조회 경로는 번호가 없으면 정렬 순번을 쓰지만 제출 경로는 번호가 없으면 null을 반환하고 행사 전체를 허용한다. A/B/C처럼 번호 없는 그룹을 늘리거나 이름을 바꾸면 화면에서 보여주는 후보 범위와 서버 허용 범위가 달라질 수 있다.

개선: 함께 만나는 장소/세션 식별자를 DB에 명시하고 조회·제출이 같은 함수를 사용한다. 이름은 표시용으로만 사용한다.

### 8. P2 — 30초 갱신 때 화면에 필요하지 않은 이력도 먼저 조회

근거: `src/features/app/AppHome.tsx:1015`; `src/app/api/meetings/my-tickets/route.ts:1435`, `:1573`, `:1621`.

프로필 등 다른 탭에서도 AppHome은 비로그인 게스트가 아니면 30초마다 티켓을 강제 갱신한다. API는 사용자의 전체 참가 이력을 가져오고 관련 행사/그룹 정보를 조회한 뒤에 페이지를 나눈다. 화면의 최초 3개 제한이 앞부분 DB 조회량을 제한하지 못한다. 그룹 조회 함수들도 일부 동일한 쿼리를 반복한다.

개선: 화면이 보이고 상태 갱신이 필요한 경우만 polling하고, 참여 중인 티켓과 과거 이력을 분리한다. 그룹 데이터를 요청 안에서 한 번 가져와 재사용한다. 실제 응답 시간과 쿼리 수를 측정한 뒤 DB 페이지네이션을 적용한다. 현재 부하 테스트로 지연 수치를 측정한 것은 아니다.

## 실행 순서

1. 피드백 쓰기 권한, 중복 신청 상태 전이, 결제 재처리, 멤버십 유효성 문제를 각각 작은 변경으로 고친다.
2. 앱/분석 검사 환경을 분리하고, 위 네 경로의 회귀 테스트를 추가한다. 기존 133개 테스트는 통과하지만 해당 실패 시나리오를 보장하지 않는다.
3. 신청·참가·결제의 상태 변경을 공통 명령/트랜잭션으로 모은다.
4. 사용하지 않는 내부 코드부터 제거하고, 티켓·피드백·프로필 영역을 나눈다.
5. 요청 수·응답 시간·번들 크기를 측정한 후 polling과 쿼리, 지연 로딩을 최적화한다.

전면 재작성보다 위 순서의 점진적 정리가 운영 중 오류 위험을 줄이면서 효과를 확인하기 쉽다.
