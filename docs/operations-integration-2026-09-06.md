# 운영 정보 통합 — 2026-09-06

## 기준 데이터

- 행사 날짜·시각·제목·지역: `meeting_events`.
- 단계별 제목·시각·공통 장소·숨김 여부: `meeting_event_stages`.
- 조별 장소: `meeting_group_stage_locations`. 조별 장소가 비어 있으면 다른 조나 공통 장소로 추정하지 않는다.
- 조의 합류 단계·피드백 범위: `meeting_groups.starts_from_stage_sequence`, `feedback_scope_key`.
- 기존 `ticket_instances`의 운영 필드는 행사 자료에서 자동 반영되는 호환용 값이다. 예약자명 등 참가 스냅샷과 프로그램 소개 문구는 별도 역할을 유지한다.

## 변경한 동작

행사 편집은 기준 데이터만 저장한다. DB 트리거가 같은 트랜잭션에서 연결된 티켓과 신청·참가 일정을 반영한다. 행사 시작 시각 변경은 각 단계의 기존 간격을 유지한다. 이전처럼 2차 장소를 저장하면서 1차 대표 장소를 덮어쓰지 않는다. 장소명·주소를 바꾸면서 지도 데이터가 그대로 남으면 이전 지도 데이터를 비운다.

참가자 티켓은 단계의 제목·장소·시각을 우선 사용한다. 장소 숨김도 우선 적용한다. 피드백 공개 시간은 명시한 피드백 단계 시각을 조회·제출에서 함께 사용하며, 단계 시각이 없으면 기존 3시간 후 기준을 사용한다. 제출 창은 공개 후 24시간이다.

그룹 이름에서 숫자를 읽던 규칙은 실행 코드에서 제거했다. 마이그레이션에서 기존 번호 규칙을 한 번 저장하고, 이후 이름 변경은 범위·합류 단계에 영향을 주지 않는다. 기존 번호 없는 그룹은 행사 전체 범위를 유지한다. 관리자 화면에서 공유 범위와 합류 단계를 수정할 수 있다. 공유 범위가 같은 조를 같은 피드백 범위로 묶고, 빈 값은 기존 행사 전체 접근을 유지한다.

그룹 이름·설정·장소 저장을 하나의 DB 명령으로 묶었다. 기존 티켓 편집에서도 행사에 속한 티켓의 운영 필드를 따로 변경하지 못하게 하되 이미지·공개 상태 등 별도 속성 수정은 유지한다.

## 상태 변경 연결

- 티켓 관리의 멤버 추가·제거 → 기존 공통 신청/참가 명령.
- 사용자 신청 취소 → 소유자·현재 상태를 DB에서 잠근 뒤 재검사, 참가 취소와 상호작용 재개까지 함께 저장.
- 결제 준비 → 최신 신청·참가 상태를 잠근 뒤 확인하고, 확정된 참가를 결제 대기로 내리지 않음.
- 결제 완료의 신청 활성화 → 공통 명령을 사용하고 확정·취소 상태를 늦은 알림으로 되돌리지 않음.
- 일회권 환불 → 결제 취소, 신청 환불, 참가 취소를 함께 저장.

결제 매칭, 외부 전환 보고, 멤버십 기간 계산은 별도 책임을 유지한다. 전체 결제 처리나 모든 운영 API를 하나의 함수에 넣은 것은 아니다. 멤버십 프로필·거래·결제 의향의 전체 원자화, 행사 생성·삭제 경로의 정리는 별도 후속 범위다.

## 검증

PGlite에서 실제 마이그레이션과 함수를 실행해 날짜·단계 간격 동기화, 2차/1차 장소 분리, 지도 데이터 정리, 숨김 처리, 기존 그룹 규칙 이관, 사용자 취소와 운영진 승인 충돌, 결제 재전송, 환불·그룹 장소 저장 실패의 전체 롤백, 함수 권한을 확인한다. 지도 객체의 키 순서와 시각 표기 차이는 운영 필드 변경으로 잘못 판정하지 않도록 검사한다.

운영 DB의 전체 데이터 복제·실결제·동시 트래픽 부하 시험을 수행한 것은 아니다.

## 적용 순서

아직 로컬 변경이며 운영 DB 적용·커밋·push·배포는 하지 않았다. 다음 순서로 적용해야 한다.

1. `20260906050350_centralize_admin_waitlist_changes.sql`
2. `20260906053936_unify_meeting_operations.sql`
3. 앱 배포

두 번째 마이그레이션은 기존 조의 규칙을 이관하고 연결된 티켓 운영 값을 행사 기준으로 맞춘다. 단계가 없는 기존 조는 장소를 유지한다. 배포 전에 대상 DB의 이관 결과를 확인해야 하며, 새 컬럼·함수를 사용하므로 앱 코드만 먼저 배포하면 안 된다.
