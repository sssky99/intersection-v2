# 운영 오류 수정 및 반복 조회 정리 — 2026-09-06

## 완료한 변경

- 멤버십: active뿐 아니라 유효한 시작일·종료일과 한국 날짜 기준 적용 기간을 검사한다. 날짜가 없거나 잘못됐거나 미래 시작인 멤버십은 현재 혜택을 적용하지 않는다.
- 중복 신청: 기존 확정 신청에는 참가 대기 전환을 호출하지 않는다. 신청 행을 수정할 때도 수정 가능한 상태 조건을 함께 검사하여 동시 승인과 충돌하면 409로 반환한다. 참가 연결은 특정 신청 id를 잠그는 DB 함수로 처리하고 이미 확정된 상태와 예약 스냅샷을 보존한다.
- 피드백: 브라우저의 직접 INSERT/UPDATE 권한을 제거하는 마이그레이션을 추가했다. 서버 검증을 통과한 피드백 저장과 참가 완료 처리는 한 DB 트랜잭션으로 묶었다.
- 결제 알림: 새 이벤트와 재전송 모두 DB의 원자적 처리 점유를 거친다. 처리 중인 요청에는 503으로 재시도를 요청하고, 중단 후 점유가 만료되면 재전송에서 복구한다. 처리 토큰으로 상태 갱신을 보호한다. 같은 이벤트의 재전송 키가 바뀌어도 원래 저장된 키를 사용한다.
- 결제 복구: 이미 일부 기록된 일회권 결제는 거래의 신청 연결을 재사용한다. 재처리 시 승인된 신청을 대기로 되돌리지 않는다. DB 요청은 개별 10초, 처리 작업은 60초 제한으로 5분 점유 만료 전에 중단하도록 구성했다. 별도 주기적 재처리 작업을 만든 것은 아니며 공급자 재전송이 복구를 시작한다.
- 미사용 코드: 예전 보증금 안내창과 저장/조회 캐시, 피드백 임시 화면, 미사용 기본정보·프로필 완료 패널 등을 제거했다. 현재 화면에서 쓰는 한도 값은 기존 공통 상수를 사용한다. 예전 브라우저 호환용 `/api/user-events` 204 응답은 유지했다.
- 반복 조회: 티켓은 관련 화면에서만, 채팅은 활성 상태에서만 갱신한다. 숨겨진 브라우저 탭에서는 polling을 중단하고 다시 보이면 갱신한다. 동일 티켓 요청을 중복 실행하지 않고 polling 자체도 이전 요청이 끝난 뒤 예약한다.
- 서버 조회: 공통 그룹 정보를 한 요청 안에서 두 번의 조회로 모아 재사용한다. 상세 행사·그룹 정보 조회는 현재 페이지 티켓으로 범위를 좁혔다. 정렬/총계 계산용 기본 참가 이력 조회 자체는 여전히 전체 이력을 사용한다.
- 검사 범위: 분석용 `analysis/` 파일이 앱 타입 검사를 막지 않도록 앱 코드의 검사 루트를 명시했다.

## 검증

`npm run check` 성공:
- 32개 테스트 파일 / 162개 테스트 통과.
- TypeScript 타입 검사 통과.
- Next.js 프로덕션 빌드 성공, 정적 페이지 43개 생성.
- `git diff --check` 통과.

PGlite를 개발 의존성으로 추가하여 별도 PostgreSQL 환경에서 마이그레이션과 실제 SQL 함수를 실행했다. 검사 항목에는 브라우저 쓰기 차단, 확정 참가 정보 보존, 피드백 저장 실패 시 전체 롤백, 결제 처리 중복 점유 방지와 만료 후 복구가 포함된다. 신청/웹훅 API 회귀 테스트와 화면 가시성에 따른 polling 테스트도 추가했다.

이는 운영 DB에서 실결제나 전체 브라우저 흐름을 실행한 결과는 아니다. 번들 제거량과 서버 응답 시간 개선을 실제 사용자 환경에서 측정한 것도 아니다.

## 운영 반영 순서

2026-09-06 운영 DB에 아래 두 마이그레이션을 적용했다. authenticated의 피드백 직접 쓰기와 신규 RPC 실행 차단, service_role의 신규 RPC 실행 권한을 확인했다. 앱 코드는 이 변경을 커밋·push한 뒤 배포한다.

아래 마이그레이션을 순서대로 적용했으며 이후 새 앱 코드를 배포한다. 새 API가 신규 DB 함수를 호출하므로 앱 코드만 먼저 배포하면 오류가 난다.

1. `20260906031238_harden_feedback_and_application_writes.sql`
2. `20260906031248_recover_interrupted_webhooks.sql`

DB 변경은 기존 테이블/데이터 삭제 없이 함수·처리 점유 필드 추가와 피드백 쓰기 권한 제한으로 구성했다. 기존 서버의 피드백 저장은 service_role을 사용하므로 해당 권한 제한과 호환된다. 적용 전 날짜가 누락되었거나 미래 시작인 active 멤버십의 운영 의도를 확인하는 것이 필요하며, 이 작업에서 개인별 멤버십 데이터를 자동 수정하지 않았다.

사용자가 기존에 수정해 둔 결제 취소 처리와 WaitlistAdminPanel 변경은 보존했다.
