# 구조 정리 1차 — 운영 상태 변경과 화면 책임 분리

## 변경한 경계

- `src/app/api/admin/waitlist/route.ts`: 관리자 인증, 요청 전달, 응답만 담당한다.
- `src/server/waitlist/readWaitlist.ts`: 운영 대기열 조회·표시 자료 구성. 기존 응답 형태를 유지한다.
- `src/server/waitlist/commands.ts`: 입력 검증, 명령 선택, DB 오류의 HTTP 응답 변환. 상태를 따로 보정하는 추가 쓰기를 하지 않는다.
- `lib/waitlistStatus.ts`: 관리자 화면과 서버가 공유하는 상태 목록과 검증.
- DB의 `admin_update_meeting_application`, `admin_update_ticket_participation`, `admin_assign_waitlist_applications`: 신청·참가·그룹 변경을 한 트랜잭션으로 실행한다.
- `src/features/feedback/TicketFeedbackForm.tsx`: 피드백 단계, 입력 상태, 사진 확대, 제출을 소유한다. 홈에서는 필요할 때 불러온다.
- `src/features/blindDates/BlindDateInvitationFlow.tsx`: 블라인드 데이트 초대·날짜 선택·도착·피드백 화면을 소유한다.
- `src/features/meetings/TicketDetailRevealHeader.tsx`: 일반 모임과 블라인드 데이트가 공유하는 표시 컴포넌트. 각 화면이 다른 대형 화면을 역으로 참조하지 않는다.
- `lib/feedbackScope.ts`: 피드백 후보 조회와 제출 검증에서 사용하는 동일한 대상 티켓 집합.

## 운영 동작 보정

1. 승인·취소와 신청 상태 저장 중 하나라도 실패하면 전부 롤백한다.
2. 조 이동과 상태·메모 변경을 함께 보낸 요청도 전부 반영한다. 이동만 요청하면 기존 상태를 유지하며, 취소자를 자동으로 승인하지 않는다.
3. 예전 참가 ID로 수정해도 연결된 신청이 있으면 같은 신청 변경 명령을 사용한다.
4. 단독 참가를 다른 티켓으로 옮길 때 이전 장소 스냅샷을 비운다. 기존 예약자명 상속 트리거가 새 장소 예약을 채운다. 대상에 별도 참가 기록이 있으면 임의 병합하지 않고 충돌로 반환한다.
5. 일괄 배정 중 일부 실패, 그룹 확정 저장 실패도 전체 롤백한다. 그룹 확정 전 조회 이후 배정이 바뀌면 다시 확인하여 충돌로 반환한다.
6. 번호 없는 그룹을 정렬 순서로 임의 해석하지 않는다. 조회와 제출 모두 기존 제출 정책을 공통으로 사용한다. 번호가 있는 기존 행사의 123/456 구분 및 7그룹 규칙은 호환을 위해 남긴다.

## 검증과 배포 조건

- 35개 테스트 파일 / 196개 테스트. SQL 실행·롤백, 관리자 인증 차단, 입력 검증, 피드백 범위 등 회귀 검증.
- PGlite에서 실제 상태 변경 함수와 예약자명 상속 트리거를 실행한다. 중간 저장 실패, 잘못된 날짜, 취소자 이동, 일괄 저장 실패, 오래된 그룹 조회, 실행 권한을 검증한다.
- TypeScript 검사와 프로덕션 빌드 검사. 실제 동시 트래픽 부하 시험, 운영 계정 브라우저 전체 흐름, 실결제 시험은 수행하지 않는다.
- 신규 함수는 SECURITY INVOKER이며 public/anon/authenticated의 실행 권한을 제거하고 service_role에만 허용한다.
- **운영 DB 적용과 배포는 아직 하지 않았다.** 배포 전에 `20260906050350_centralize_admin_waitlist_changes.sql`을 먼저 적용해야 한다. 신규 코드만 배포하면 대기열 수정 API가 신규 함수를 찾지 못한다.
- 이번 작업에서는 커밋·push를 하지 않았다.

## 다음 정리 순서

1. 장소·일정·피드백 세션을 행사/단계 데이터에서 명시하고 관리자 편집 화면과 함께 연결한다. 기존 행사 값을 검증한 뒤 이름 기반 호환 규칙을 제거한다.
2. 티켓 관리 API와 결제 경로에 남은 상태 변경을 같은 명령 경계로 점진적으로 옮긴다. 이번에 모든 쓰기 경로를 통합한 것은 아니다.
3. 홈의 티켓 조회·페이지·갱신 상태와 신청 화면의 결제 흐름을 각각 분리한다.
4. 현재 참가와 과거 이력을 분리한 DB 페이지 조회를 도입한다. 기존 정렬·총계와 일치하는지 검증한 뒤 전체 기본 이력 조회를 제거한다.

운영 명단, 이미지, 준비된 메시지, 분석 파일과 기존 임시 파일 변경은 이번 작업 범위에 포함하지 않는다.
